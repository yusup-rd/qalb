# Qalb Quran content provenance and packaging

## Why the app no longer ships `quran.db`

Quran.Foundation's [Developer Terms](https://api-docs.quran.com/legal/developer-terms/)
(version last updated 11 October 2026, reviewed 24 October 2026) allow QF
Content to be displayed in an app experience and permit offline storage obtained
and maintained through Content Sync, subject to a sync at least every seven
days when connectivity permits. The same terms explicitly say that this
storage exception does not authorize distributing a prepackaged database or
build-time bundle. Redistribution of QF Content or raw API data requires a
separate signed commercial license. Content Sync's
[offline-cache guidance](https://api-docs.quran.com/docs/tutorials/content-sync/offline-cache-patterns/)
also requires Content Sync as the only path for acquiring and maintaining an
offline copy when a resource is supported.

The former `apps/mobile/assets/database/quran.db` was referenced as an Expo
SQLite asset and therefore copied into a new installation. It has been removed
from the repository and app packaging. Existing installations' app-private
`quran-v2.db` files are not deleted or renamed. When online, the app refreshes
them from Qalb's API; a new installation downloads its first complete dataset
before enabling Quran reading. A successful initial snapshot is committed in
one SQLite transaction, including its revision. Failed or invalid downloads do
not mark a first installation initialized or replace a previously committed
database.

## What could be established about the former database

The database was first committed in `b70421f`, before the checked-in seed
script existed, and contains no source, author, license, attribution, or
provenance tables. Git therefore does not prove the exact origin of the bytes
in that initial database. Its rows contain 114 chapters, 6,236 verses, English
translation resource 85, Russian translation resource 45, transliteration
resource 57, and ayah audio metadata for recitation 6. These resource IDs and
the content shapes match the later mobile seed script's declared mapping.

That seed script fetched regular QF Content API snapshot endpoints for
`quran_core:1`, `translations:85`, `translations:45`, `translations:57`, and
`recitations:6`, then wrote the resulting records into the build-time SQLite
file. It did not use Content Sync. The database contains URLs on
`mirrors.quranicaudio.com` for recitation audio and stores no audio recordings;
its reciter row only says `Reciter 6`, while the About screen credits Mahmoud
Khalil Al-Husary and the URL path includes `Husary_64kbps`. [QuranicAudio says
its files are free for personal use, not commercial use, and that files come
from different sources](https://quranicaudio.com/about). Those statements and the app's attribution do not
identify the specific recording rights holder or grant Qalb streaming,
redistribution, or caching permission. The script's mapping is evidence of the
intended sources, not proof that the original database bytes were generated by
that script or that each underlying work may be redistributed. The generator
has been removed so a routine seed command cannot recreate a prohibited
prepackaged content database from regular API responses.

No per-resource license or creator metadata was preserved for the two
translations or transliteration. Their precise authorship, attribution, and
any rights beyond the display/offline rights expressly granted by QF remain
unverified. The Quran text's exact digital edition/provenance is also not
recorded. QF's API terms do not themselves establish that a third-party
recitation recording may be redistributed or cached; audio recording rights
remain a separate unresolved issue. Audio URLs and metadata are still part of
the QF Content Sync projection and are not bundled in the mobile application.

## Live data path and requirements

The API maintains `quran_core:1`, translation resources `45`, `57`, and `85`,
and recitation metadata `6` through QF Content Sync using credentials held only
on the backend. The mobile app obtains a complete app projection through the
Qalb API. It validates the core counts, both translation resources,
transliteration, audio metadata, relationships, and snapshot revision before
committing. Incremental changes and their revision are applied transactionally
and validated before commit. The app attempts sync at launch, on foreground,
and when network connectivity returns. It also registers an Expo background
task with a 24-hour minimum interval. The OS may defer this task, and stopping
the app can stop background execution until the next launch; a mobile app
cannot guarantee an exact seven-day execution deadline on iOS. The backend
checks QF Content Sync weekly and starts a due catch-up when status is
requested. After first download, local reading and search work offline.

A first installation without internet cannot read Quran content until its
first successful download. The startup screen says so and offers retry. No QF
credential is included in the mobile bundle. This design does not establish
rights to use or redistribute individual translations or recitation
recordings; it complies with the prepackaging restriction by not shipping the
content database.

The scheduled device task is best effort rather than a hard weekly guarantee.
Before release, validate scheduling on real iOS and Android devices and decide
whether QF accepts platform-controlled background execution limits. The app
refreshes promptly when a user opens it or connectivity returns while it is
running.

## Questions requiring provider confirmation

Before release, request written confirmation from Quran.Foundation that it is
authorized to grant the in-app display and Content Sync offline-cache rights
for these exact resources, and obtain the resource creators, exact attribution
text, and any additional conditions:

- `translations:85` (English)
- `translations:45` (Russian)
- `translations:57` (English transliteration)
- `quran_core:1` (digital Quran text and chapter metadata)
- `recitations:6` (recitation metadata and audio URLs)

Do not ask whether ordinary API access allows bundling: the published terms
already say it does not. The specific permission needed to restore any bundled
database is a signed commercial license that expressly authorizes distributing
the named QF content as an integrated build-time database inside the Qalb app
installer, on both iOS and Android, including its translations and metadata.
Separately confirm playback/streaming rights for the exact Mahmoud Khalil
Al-Husary recordings with their respective rights holders and QuranicAudio;
Quran.com states it does not own or license the recitations on its apps
[either](https://feedback.quran.com/reciters-request/p/permission-request-using-quran-recitation-audio-in-monetized-youtube-content).
Qalb does not treat the URL, QF resource ID, or QuranicAudio's personal-use
statement as permission for embedding or streaming within this app.
